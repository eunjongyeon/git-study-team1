1번 부질문
팀원 각자 저장이랑 커밋이 뭐가 다른지, 본인 나름대로 이해한 대로 2\~3줄씩 써주세요.
교과서적으로 작성하지 않으셔도 됩니다.
은종연

* 저장은 수정한 내용을 부분마다 개인적으로 저장하는 것이고, 커밋은 그렇게 수정이 완료된 파일을 Push해서 협업을 위해 공유하거나 서버로 올리기 위해 사용하는 기능이다.



정예진

* 저장과 커밋의 다른 점: 저장은 덮어씌우기, 커밋은 수정사항이 담긴 세이브파일을 세이브슬롯에 시점별로 세이브하기



조명주

* 저장은 이때까지 한 기록을 모두 한꺼번에 기록한 것이지만, 커밋은 내가 수정한 부분을 기록한 것이다.(저장보다는 조금 더 세부적인 부품을 기록한다는 느낌으로 이해했습니다.)



최종현

저장은 로컬 단위에서 데이터를 기록하는 느낌이라면,

커밋은 로컬의 내용을 서버에 올리기 위한 과정이라고 생각한다!

save라는 개념은 비슷해도 관할하는 영역이 다른 것 같다.


강진규

* 저장은 히스토리가 남지 않지만(보장하지 않지만), 커밋은 명시적으로 체크포인트를 만들어 원하는 시점을 저장내역을 남길 수 있음.











2번 부질문
은종연
언제/왜 Pull을 먼저 했는지, 안 하면 어떻게 되는지 겪어봤다면 그 얘기도

* 다른 팀원이 push 했을 때, 겪어보진 않았는데 push가 리젝되는 걸로 알고 있음
Commit 메시지 뭐라고 썼는지, Push 눌렀을 때 결과가 어땠는지
* 파일 만들었으면 제작, 내가 한 거 간단하게 작성 타인이 이해할 수 있도록
본인 차례를 기다리는 동안 다른 사람 화면에서(혹은 GitHub Desktop History 탭에서) 뭐가 보였는지
* 다른 사람이 commit한 내용, 제목, 그리고  No newline at end of file이라는 문구



정예진
언제/왜 Pull을 먼저 했는지, 안 하면 어떻게 되는지 겪어봤다면 그 얘기도

* 어차피 pull을 먼저 하게 되어 있는 것 같긴한데 안한다면 내가 push 한 게 거절되고 pull 먼저 하라고 함.
Commit 메시지 뭐라고 썼는지, Push 눌렀을 때 결과가 어땠는지
* 업데이트 내용 간략하게 요약해서 메세지 씀. 내 로컬파일과 팀원 로컬파일이 갱신됨.
본인 차례를 기다리는 동안 다른 사람 화면에서(혹은 GitHub Desktop History 탭에서) 뭐가 보였는지
* 몇 분 전에 패치가 되었는지도 보였고, 패치를 하면 팀원들의 수정사항이 계속 갱신됨. 새로 추가된 것과 빠진게 뭔지 확인할 수 있도록 커밋별로 색 구분이 되어있음



조명주

* 순서대로 팀원이 작성을 완료하면 pull 했음
* 커밋 메세지에는 어떤 내용을 적었는지 요약해서 적음. push를 하니, 커밋 부분이 사라짐
* 하나씩 히스토리가 추가되었음



최종현

\*언제/왜 Pull을 먼저 했는지, 안 하면 어떻게 되는지 겪어봤다면 그 얘기도

앞선 팀원의 commit이 완료된 것을 확인하고 수정한 결과를 받아오기 위해서 pull을 했고, 안 하지는 않았다.



\*Commit 메시지 뭐라고 썼는지, Push 눌렀을 때 결과가 어땠는지

commit 메시지는 4번째 업데이트라고 처음에 적고, 두 번째에는 귀찮아서 업데이트만 적었다.

내용을 적지 않아도 커밋에는 문제가 없었다.

push를 누르자 리포지토리로 올라갔다.



\*본인 차례를 기다리는 동안 다른 사람 화면에서(혹은 GitHub Desktop History 탭에서) 뭐가 보였는지

fetch버튼이 보이고, 마지막으로 fetch한 시간이 언제인지 나왔다.

버튼을 누르자 pull 내역이 있다는 표시와 숫자가 나왔다.

숫자는 commit된 숫자를 의미할 것이다.


강진규

* 다른 팀원들이 푸시했다고 한 이후에 패치와 풀을 진행함.
* 작업 내용을 요약하여 커밋 메시지 작성함. 잘 Push 됨.
* pull 하기 전에는 아무 변동사항을 볼 수 없었음. 패치 후 풀까지 완료하면 팀원들이 변경한 사항을 확인할 수 있음.

3번 부질문
브랜치는 각자 뭐라고 이름 지었는지
merge를 총 몇 번 했는지, 순서대로 어떻게 진행했는지
충돌은 어느 파일, 어느 줄에서 났는지, 화면에 뭐가 떴는지, 어떻게 골라서 해결했는지

은종연
* 브런치는 과제에 명시된 feedback에 본인이름을 영문으로 붙였다.
* merge는 5명 팀으로 총 다섯 번 진행했다.
* 충돌은 review.md 파일에서 발생했으며 solve conflicts가 떴으나 클릭하지 않았다. 실무에서는 해당 방식으로 수정하는 것이 아니라 각 담당자에게 직접 충돌난 부분의 수정을 요청한 뒤 수정된 Pull Request를 확인하고 merge 한다고 해서 해당 방식으로 진행했다. 충돌이 난 줄은 같은 줄을 기입한 부분이었다.
